# 文档维护规范

NovaLink 的项目文档和 GitHub Wiki 都是运行与集成契约的一部分。维护文档的目标不是把代码注释搬运成宣传文案，而是让读者能够追溯关键事实、识别实现边界、复现操作并理解未验证的限制。代码、示例配置和已提交的验证材料优先于记忆、聊天记录或过期截图。[1]

## 1. 权威来源地图

| 主题 | 首要来源 | 次要核验来源 | 文档页面 |
| --- | --- | --- | --- |
| 后端启动、端口、服务装配 | `StarLink/core/.../NovaLinkMain.java` | `examples/novalink.yml` | 快速开始、部署、架构。 |
| YAML 解析与热重载 | `ConfigLoader.java`、`ConfigManager.java` | 示例配置 | 配置、安全、运行手册。 |
| 频道和路由 | `ChannelManager`、`MessagePipeline`、`MessageRouter` | 后端测试 | 配置、架构、协议。 |
| REST | `RestApiHandler.java`、`HttpAuthHandler.java` | 面板 API 服务 | 管理 API、安全。 |
| WebSocket | `WebSocketMessageHandler.java`、`WebSocketGateway.java` | 面板 WS 服务/上下文 | 实时网关、部署。 |
| 接入端协议与恢复 | `NovaChat/common`、`NovaChat/client-core/DESIGN.md` | 平台模块实现 | 协议与客户端、架构。 |
| 构建与模块 | `settings.gradle`、`build.gradle`、子模块构建文件 | CI 配置/构建日志 | 开发与测试、贡献。 |
| 真实环境验证 | `e2e/README.md`、E2E 脚本、锁定文件 | 运行结果 | 开发与测试、Wiki 排障。 |

当来源之间冲突时，优先选择当前分支中实际被运行路径引用的实现，并在文档中标明不确定性或待验证边界。不要为追求“完整”而猜测字段、默认值、端点或平台兼容性。

## 2. 更新触发条件

| 发生的代码或配置变化 | 必须审阅的文档 | 必须确认的事实 |
| --- | --- | --- |
| 端口、启动参数、JAR 产物、数据库提供者 | 快速开始、部署、安全 | 命令、路径、默认行为、回退要求。 |
| YAML 字段、默认值、热重载 | 配置、运行手册、Wiki 配置页 | 是否被解析、是否会热应用、是否会同步给客户端。 |
| 认证、管理员、token 或允许 IP | 安全、管理 API、部署 | access/refresh token 边界、网络暴露和轮换影响。 |
| 频道、权限、世界过滤或路由 | 配置、架构、协议、运行手册 | 作用域、扇出范围、平台限制、治理影响。 |
| REST 路由或 JSON 字段 | 管理 API、Wiki API 页 | 方法、路径、认证、请求体、响应、状态码。 |
| WebSocket 类型或负载 | 实时网关、Wiki 网关页 | 鉴权时序、订阅范围、字段、周期推送行为。 |
| 平台/Loader/JDK/API 兼容性 | 协议与客户端、测试、README | 实际验证平台与未验证组合。 |
| 控制台命令、通知、治理行为 | 运行手册、Wiki 运维页 | 命令可用性、参数、影响范围与回退。 |
| E2E 脚本/平台矩阵 | 开发与测试、Wiki 测试页 | 前置条件、模式、版本、结果和已知限制。 |

## 3. 写作和证据规则

每份稳定技术文档应满足以下规则：

| 规则 | 做法 |
| --- | --- |
| 绑定事实来源 | 对端口、命令、字段、路由、消息类型和平台状态提供仓库内链接或引用。 |
| 区分当前与规划 | 对未解析 YAML 段、未来想法、历史验证或平台差异明确使用“未由当前实现读取”“待目标环境验证”等措辞。 |
| 保留安全边界 | 用 `<access-token>`、`<database-password>` 等占位符替代真实值；不复制生产 IP、Webhook 或玩家数据。 |
| 写出验证动作 | 部署/运维步骤必须包含完成后的观察或测试，而不止是命令。 |
| 解释影响范围 | 对重载、治理、断连、开关和 API 调用说明数据面/控制面影响。 |
| 使用稳定术语 | 保持 NovaLink、NovaChat、NovaProtocol、Admin Console、管理网关、接入端等名称一致。 |
| 控制重复 | 仓库文档保存完整可审阅细节；Wiki 提供导航、操作摘要和指向权威页面的链接。 |

## 4. Wiki 维护规则

GitHub Wiki 应面向读者的任务路径，而非镜像整个源码树。每个 Wiki 页面应拥有清晰标题、简短目的说明、到相邻页面的导航、到仓库权威资料的链接和必要的安全提醒。

| Wiki 页面类别 | 应包含 | 不应包含 |
| --- | --- | --- |
| 首页 | 产品定位、角色入口、主要导航、文档版本提醒 | 长篇接口负载、真实密钥、未经证实的兼容承诺。 |
| 快速开始 | 最小接入链路、下一步、常见失败点 | 复制所有部署/配置细节。 |
| 配置/部署 | 高层决策、关键字段、验证路径 | 未解析 YAML 的“即配即用”说明。 |
| API/实时网关 | 端点/消息类别、认证、链接到详细参考 | 不安全的 token/生产 URL 示例。 |
| 排障 | 现象到检查路径、升级信息 | 让用户直接删除数据或关闭安全控制的建议。 |

当 Wiki 与仓库文档发生冲突时，先修复仓库内的版本化事实来源，再更新 Wiki 摘要。发布 Wiki 前检查 `_Sidebar.md` 是否可到达所有页面，并检查仓库 URL 是否使用稳定默认分支链接或相对语义。

## 5. 发布前审阅

在提交文档或推送 Wiki 之前，执行以下核对：

| 检查 | 通过条件 |
| --- | --- |
| 路径与链接 | 所有相对链接、外部仓库链接和 Wiki 侧栏链接可到达。 |
| 代码事实 | 端口、构建命令、配置字段、端点和 WS 类型逐项与当前源文件对照。 |
| 配置边界 | 规划性/未解析字段没有被写成当前生效功能。 |
| 安全卫生 | 没有真实密码、token、私有 IP、Webhook URL、数据库凭据或敏感日志。 |
| 术语一致 | 目录名、模块名、客户端/后端角色与 README 一致。 |
| 操作可验证 | 每条高影响指引都给出观察、测试或回退条件。 |
| 变更范围 | Git 差异只包含预期文档、README、计划和 Wiki 内容。 |

## 6. 审阅提示词

维护者在审阅一段文档时，可以用以下问题快速发现风险：

> “这一句是在描述当前代码、示例值、历史测试结果，还是未来设想？读者能否从本仓库中打开一个来源来验证它？”

如果无法回答，应缩小陈述、补充来源、标记不确定性，或删除没有证据的内容。技术文档的可信度来自可验证的边界，而非将所有可能性都写进去。
