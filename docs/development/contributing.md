# 贡献指南

NovaLink 的贡献跨越后端、协议、平台适配、管理面板、构建和真实环境验证。高质量贡献不仅是“代码能编译”，还应让维护者能够判断：改动放在正确的模块了吗？影响哪些平台和控制面契约？已经运行了哪些验证？仍有哪些未验证的风险？[1] [2]

## 1. 开始前

在开始编码前，请先检查仓库 Issue，避免重复实现或遗漏已有的平台兼容性讨论。对涉及协议、频道范围、认证、治理、数据库、管理 API 或平台线程模型的改动，建议先说明问题、目标、非目标和验证范围，再进入实现。[3]

| 变更类型 | 开始前必须确认 |
| --- | --- |
| 新功能 | 谁使用、受哪个权限控制、是否需要配置/API/面板支持。 |
| 协议修改 | 旧接入端行为、版本边界、编码/解码与失败模式。 |
| 平台适配 | 目标平台、Minecraft/Loader/JDK 版本、生命周期与线程限制。 |
| 后端路由/治理 | 频道作用域、跨服影响、审核/回退方式。 |
| 前端控制面 | REST/WS 契约、认证、错误显示与代理部署。 |
| 文档改动 | 事实来源、受众、链接和是否涉及安全敏感内容。 |

## 2. 模块边界

贡献应遵守当前架构的依赖方向。协议包和编解码属于 `NovaChat/common`；接入端可复用生命周期能力属于 `NovaChat/client-core`；独立生产后端业务属于 `StarLink/core`；玩家 UI、平台事件和平台调度应留在对应适配模块。[1]

| 不应做的事 | 原因 |
| --- | --- |
| 让 `StarLink/core` 依赖 `NovaChat/client-core` | 会把接入端运行时反向带入后端。 |
| 把 Bukkit/Folia/代理玩家 API 放进共享协议模块 | 会破坏跨平台和无平台后端边界。 |
| 因一个平台的体验需求改写所有平台的网络假设 | 各平台线程、事件和配置格式不同。 |
| 未经审阅扩大全局频道、客户端权限或管理 API 暴露 | 可能改变消息可见性与权限边界。 |
| 把未验证的未来配置写成现有功能 | 会误导部署者并造成高风险操作。 |

## 3. 分支与提交

保持提交集中、可审阅且可回滚。一个提交应尽可能只解决一个完整的逻辑问题，例如“修复握手错误码处理”或“为设置页增加已实现的功能开关”。不要把构建产物、临时日志、真实服务端二进制、IDE 缓存或无关格式化混入功能提交。

推荐的提交信息示例：

```text
fix(core): reject refresh tokens on websocket auth
docs(operations): clarify configuration reload verification
test(e2e): cover bukkit to velocity chat round trip
feat(panel): surface client disconnect notifications
```

提交前使用 `git diff --check` 和 `git status` 审阅改动边界。涉及多个独立子系统时，拆成可单独审阅、单独验证的提交会比一个大提交更安全。

## 4. Pull Request 必填信息

每个 PR 描述应使用完整句子说明下表内容：

| 项目 | 需要说明的内容 |
| --- | --- |
| 问题与目标 | 解决了什么问题，为什么当前行为不足。 |
| 影响范围 | 受影响的模块、平台、配置、API、WebSocket、面板和文档。 |
| 行为变化 | 成功路径、失败路径、权限/频道范围变化与回退方式。 |
| 验证证据 | 实际执行的命令、平台环境、结果与未运行的测试。 |
| 风险与限制 | 未验证的平台、依赖的上游版本、性能/兼容性风险。 |
| 安全与数据 | 是否触及凭据、令牌、管理员、日志、玩家数据或外部 Webhook。 |
| 文档 | 已更新的项目文档/Wiki 页面，或不需要更新的明确理由。 |

对平台改动，不要只写“已测试”。至少说明平台名称、运行时/版本、JDK（如相关）、接入状态、消息路径和是否测试过后端断开后的恢复行为。

## 5. 验证标准

验证应从最接近改动的最小测试开始，再根据风险扩大。常用入口如下：

```bash
./gradlew :StarLink:core:test
./gradlew check
./gradlew build

cd Panel/web
npm run build
```

真实 E2E 是一条显式选择的验证路径，需要实际服务端、机器人与平台运行时。它不会随普通构建默认执行。若 PR 改动协议、跨服消息或平台适配，请说明为什么运行或未运行了相关真实环境验证。[2] [4]

| 改动 | 最少应提供的验证 |
| --- | --- |
| 后端纯逻辑 | 对应模块测试和受影响 API/配置的复核。 |
| REST/WS | 后端测试、请求/负载对照，以及面板连接或独立客户端验证。 |
| 平台插件/代理 | 编译、目标平台 smoke、握手/消息/停用验证。 |
| 多端路由 | 至少一条端到端消息路径；高风险改动考虑真实 E2E。 |
| 前端 | `npm run build`，并验证受影响的登录/API/WS 状态。 |
| 文档 | 事实来源、相对链接、命令与敏感信息扫描。 |

## 6. 安全与数据卫生

严禁在 Issue、PR、截图、日志、示例配置或 Wiki 中提交以下内容：真实客户端密码、JWT/refresh token、数据库密码、私有 IP、生产 Webhook URL、玩家个人数据、未脱敏日志或下载的商业/受限二进制。

如果排障必须提供配置，请使用可复现的最小匿名化样例，并把所有高熵字符串替换为清晰占位符，例如 `<access-token>`、`<database-password>` 和 `203.0.113.0/24`。不要仅通过删掉用户名就认定日志已经脱敏。[5]

## 7. 文档是功能的一部分

以下变化通常要求同步更新文档：

| 代码变化 | 至少审阅的页面 |
| --- | --- |
| `NovaLinkMain`、配置模型或加载器 | [配置指南](../guide/configuration.md)、[部署指南](../guide/deployment.md)。 |
| `RestApiHandler` 或 `HttpAuthHandler` | [管理 API](../reference/admin-api.md)。 |
| `WebSocketMessageHandler` / 前端 WS 服务 | [实时网关](../reference/realtime-gateway.md)。 |
| `NovaChat/common` / `client-core` | [架构参考](../reference/architecture.md)、[协议与客户端](../reference/protocol-and-clients.md)。 |
| 控制台、治理、通知 | [运行手册](../operations/operations-runbook.md)。 |
| 构建、E2E、平台版本 | [开发与测试](development-and-testing.md)。 |

更新 GitHub Wiki 时，优先更新入口、快速操作和排障导航，并链接到仓库中的版本化详情。文档维护者应保证 Wiki 不承诺仓库文档与代码没有证明的行为。[6]

## 8. 审阅者检查表

| 检查项 | 审阅问题 |
| --- | --- |
| 责任归属 | 改动落在协议、接入端、后端还是平台层的正确位置？ |
| 向后兼容 | 客户端、配置、API、存储或面板是否受到影响？ |
| 安全 | 是否扩大了网络、token、权限或数据暴露范围？ |
| 平台差异 | 是否错误地把一个平台的线程/生命周期假设推广到所有平台？ |
| 验证 | 命令、环境和结果是否足以支撑改动声明？ |
| 文档 | 关键行为、限制和操作步骤是否已同步？ |
| 可回退性 | 若生产行为不符合预期，是否能安全回退？ |
